Stream（流式）和 Non-stream（非流式）决定的是模型生成结果怎么传回客户端：前者边生成边吐字，后者等整条回复生成完再一次性返回。

## 核心区别

> **Stream（流式输出）｜逐步返回**
>
> 1. 收到第一段时，用户看到「你好」。
> 2. 下一段接在同一条回复后面，变成「你好，我可以」。
> 3. 收到最后一段，整句才显示完整：「你好，我可以帮助你。」

> **Non-stream（非流式输出）｜一次性返回**
>
> 1. 模型生成回复时，用户还看不到正文。
> 2. 生成完成后，用户一次看到整句：「你好，我可以帮助你。」

## 具体对比

| 维度           | Stream                                                       | Non-stream                                                     |
| -------------- | ------------------------------------------------------------ | -------------------------------------------------------------- |
| 返回方式       | 通过 SSE 分段推送                                            | 等全部生成完，一次返回完整 JSON                                |
| 首字可见时间   | 极快，模型吐出首批 token 后就能渲染                          | 慢，必须等整条回复生成结束                                     |
| 网关超时与断连 | 首包快、不易触发网关首字节超时，但需要维持长连接             | 1. 长耗时请求容易撞上网关超时<br>2. 中途断连拿不到任何部分结果 |
| 客户端复杂度   | 较高，要处理分段拼接、事件解析和中途断线                     | 很低，直接解析一次完整的 JSON                                  |
| 中途取消       | 1. 断开连接即可<br>2. 服务端写后续分片时更容易感知并中止生成 | 1. 可取消请求<br>2. 服务端是否立刻停止生成取决于具体实现       |

> [!NOTE] Note
> 开启流式输出只是让用户更早开始读第一段，模型生成整条回复的总耗时并不会因此变短

## 请求与响应长什么样

以常见的 OpenAI 兼容 Chat Completions 接口为例（响应仅保留关键字段）。

### Stream

请求体加上 `"stream": true`：

```json
{
  "model": "Gemini 4 Carbon",
  "messages": [
    {
      "role": "user",
      "content": "你好"
    }
  ],
  "stream": true
}
```

服务端通过 SSE（Server-Sent Events）持续推送分片，直到 `[DONE]`：

```text
data: {"choices":[{"delta":{"content":"你"}}]}

data: {"choices":[{"delta":{"content":"好"}}]}

data: {"choices":[{"delta":{"content":"！"}}]}

data: [DONE]
```

客户端把每个分片的 `delta.content` 依次拼起来，就能实时显示「你好！」。这里为了演示把分片写成了单字，实际线上的每个 chunk 并不一定刚好对应一个汉字或一个 token。

如果用的是 Responses API，同样支持流式输出，不过改成了按事件类型区分正文和函数参数，具体可看[两套接口的流式输出对照](/posts/chat-completions-responses/#接口)。

### Non-stream

请求体设为 `"stream": false`（或不传，多数接口默认非流式）：

```json
{
  "model": "Gemini 4 Carbon",
  "messages": [
    {
      "role": "user",
      "content": "你好"
    }
  ],
  "stream": false
}
```

服务端等生成彻底结束后，返回完整 JSON：

```json
{
  "choices": [
    {
      "message": {
        "role": "assistant",
        "content": "你好！"
      }
    }
  ]
}
```

## 什么时候用 Stream

判断标准很简单：**在完整结果出来之前，调用方拿不完整的数据可以做什么？** 只要能提前消费（比如实时渲染、分段播报），就使用 Stream。必须等完整数据校验通过才能继续的，只能用 Non-stream 了。

以「识别一张菜单照片」为例，不同场景的选型完全不同：

| 场景                 | 建议       | 原因                                                         |
| -------------------- | ---------- | ------------------------------------------------------------ |
| 实时给用户念菜单     | Stream     | 第一道菜名和价格刚出来就能先播报，不用干等整张菜单识别完     |
| 识别后直接录入数据库 | Non-stream | 必须拿到完整的菜名、价格和币种做字段校验，半截 JSON 没法入库 |
| 聊天窗口展示长回答   | Stream     | 减少等待焦虑，用户能边看开头边等下文（打字机风格～）         |
| 后台定时生成日报     | Non-stream | 无人在意过程，直接获取最终结果                               |

另外有两个常见误区：一是流式吐出来的是识别文本本身，不是「图片分析进度条」，二是实时音视频通话需要双向全双工接口，单靠 `stream: true` 解决不了。

## 做多模型兼容层时的注意点

如果要封装一层兼容多个厂商（OpenAI、DashScope、豆包等）的调用网关，建议同时接通 Stream 和 Non-stream，并对上层吐出统一的最终结果结构（正文、Token 用量、结束原因、错误信息、工具调用）。

实践时需要注意：

- **工具参数按调用分路拼接**：流式模式下正文按顺序拼，但模型可能一次发起多个工具调用，参数片段必须按各自的调用 ID 或索引分开拼，不能混成一团。
- **断线不等于完成**：在收到明确的结束信号（如 `[DONE]` 或结束事件）前如果连接断了，前面收到的半截正文和参数只能标记为失败或丢弃，不能拿着半截 JSON 去触发工具执行。
- **用量缺失记为未知**：不同厂商在流式模式下返回 `usage` 的时机和开关不一样，没拿到用量时建议标记成未知（`null`）。
